Siyagah — Independent Audit Handover

Prepared: 18 September 2026 Prepared by: Claude (Claude Code session), at the owner's request Prepared for: an independent architecture, quality and usability audit by ChatGPT Audience of this document: the owner (a non-programmer) first, the incoming auditor second

1. Executive summary — in plain language

Siyagah is a personal notes app. It is unusual in one important way: the whole application is a single file, index.html — about 1.2 MB of markup, styling and roughly 18,000 lines of JavaScript, with no build step, no frameworks and no package manager. You open that one file and you have the app.

The headline for a non-programmer:

The app is in good working order and noticeably more carefully built than most one-person projects — it has a genuine automated test harness, a written set of rules it refuses to break, and an unusually honest history. But this audit found three real faults, one of which could silently erase a note you had just written. All three are now fixed and proved fixed — with one important exception: the same private data is still published in the app's sealed "frozen build", which the project's own rules forbid me from editing without your say-so.

The three faults, in order of seriousness:

The important thing to understand about all three: the app's own automated tests were passing 266 out of 266 when these faults were present. They were not in code the tests got wrong — they were in places the tests had never thought to look. That is not a criticism of the harness, which is genuinely good; it is the normal limit of any test suite, and it is exactly why an outside audit is worth doing.

What this session did not do: nothing was merged, nothing was deployed, and no data operation was performed on your live notebook. The work sits on a branch waiting for you.

3. What the app is, in plain language

Purpose

A private knowledge notebook for one person. Notes live in folders, folders live in sections, and a set of automatic "Smart Views" slice the same notes different ways. It is explicitly single-user: one Google account, one notebook, no sharing, no collaborators, no second person's data anywhere in the design (decision D1).

The main journeys

  1. Write a note. Press ✚ Note; the note opens in its own pop-out window. Type into it; it saves itself as you go.
  2. Organise. Put notes in folders (a note can be in several), tag them, give each a single "Note Type", pin them, favourite them, archive them.
  3. Find. Search from the sidebar; or use a Smart View; or filter by tag or type.
  4. Read and revise. Notes have headings that fold, a contents panel, note history, reminders, and a spaced-review view (Murāja'ah).
  5. Keep it safe. It saves to the browser, optionally to a file on your disk, to a downloadable copy of the whole app, and to the cloud.

Features that genuinely work

Verified present and functioning during this audit unless marked otherwise.

Notes and editing — rich text (bold/italic/underline/strikethrough, colour, text size, alignment), headings that fold, tables, images, links, embeds (YouTube/Vimeo), quick phrases, templates, "mark done" and boundary-box styling, per-note history with restore, note versioning, annotations.

Organisation — sections → nested folders → notes; a note may sit in several folders; tags (multiple, colour-codable); Note Types (single-select, user-editable, grouped into categories); folder groups; a pinned tab bar that is per note; favourites; archive; Trash with restore.

The 11 Smart Views — New Articles, Recently Edited, Favourites, Pinned, Timeline, Daily Journals, Archived Notes, MyWall, Reminders, Murāja'ah Review, In Practice.

Beyond notes — a calendar with categories and public-holiday lookup, a journal, a contacts module (free-text and structured-form modes), a small "My Database" record feature with reports and presets, reminders.

Appearance — five colour presets (Forest, Ocean, Amber, Indigo, Rose) plus custom sidebar/paper/accent colours, with the app deriving readable text colours from whatever you pick. This has had an unusual amount of measured attention (five rounds of WCAG contrast work).

Platform — three genuinely different layouts (phone <640px, tablet 640–1199px, desktop 1200px+), installable as a PWA, works offline.

Features that are planned or partial

  • Merge on JSON import. The HTML-backup importer offers "merge or replace"; the JSON importer only replaces. Left as an open product decision (§7).
  • A real dark mode. The codebase explicitly records that inverting text is unsafe because notes carry pale decorative bands; a true dark mode is noted as "a round, not a variable" and has not been done.
  • Accessibility beyond colour. Colour contrast is extensively measured; keyboard navigation, screen-reader semantics and focus management are essentially unaddressed (§6, Finding 4).

Sync and merge

mergeDB(local, remote) unions both sides and lets the newest edit win per record — it never picks a winning device (invariant I2). It is more careful than most hand-rolled merges:

  • per-collection merge by id on updatedAt;
  • a permanent tombstone log keyed by the deleted record's id, so emptying Trash cannot resurrect deletions on a device that had not yet synced them;
  • separate stamp maps for object-shaped settings (tagColorsAt, uiAt, tabsAt, tabsX) so scalar settings have something to compare;
  • _flushAllEditors() before a push, so the cloud receives what is on screen rather than what the 1.2-second autosave last committed.

Authentication

Google sign-in via Firebase Auth (compat SDK 9.23.0), loaded from gstatic.com at runtime. The signed-in Google UID is the notebook ID, so each account is isolated by construction. A one-time migration copies an old random-ID notebook to the UID path. With no sync configured, initAuth() returns early and the app is fully usable with no sign-in at all.

6. Findings, ranked

Finding 1 — CRITICAL — A note open in a pop-up could be silently emptied

Invariant broken: I1 — "No note, folder or section is ever lost or silently changed." D3 does not excuse it: this is not a deliberate deletion via Trash.

Reproduction (real mouse clicks only, repro/note-wipe-real-clicks.mjs):

1. Click ✚ Note        → the note opens in its own pop-up (normal since v04.00)
2. Click ✏ Edit        → in Pane 3, visible behind the pop-up
3. Type into the pop-up
4. Click another folder
   → the note's content in DB becomes ""

Before (v04.34, commit ba6c70f):

tablet  (820x1180): 3. typed into pop-up → DB: "MY IMPORTANT NOTE TEXT"
                    4. moved to folder 2 → DB: ""
                    VERDICT: *** NOTE SILENTLY EMPTIED ***
desktop (1440x900): VERDICT: *** NOTE SILENTLY EMPTIED ***
phone   (390x844) : Edit button not clickable (sheet covers it) → note intact

After (v04.35): all three sizes VERDICT: note intact.

Mechanism. Step 2 built a second editor (#ed) on a note that the pop-up (.fw-ed) already owned. At that instant the note really was empty, so #ed was correctly empty. The typing in step 3 went to the pop-up. In step 4, selFolder() calls saveArt(), which reads #ed — the stale empty one — and commits it over the live note. persist() then pushes the empty result to every other device.

This was proved, not inferred, by trapping the property itself:

Object.defineProperty(a, 'content', { set(nv){ log(new Error().stack); … } });
// → "REPRO CONTENT MARKER" -> ""   at saveArt … at selFolder

Why no test caught it. The app's rule "hand-over, never duplicate" was enforced by popOutNote() in one direction (pane → pop-up, extended to Pane 3 in v04.33). Nothing enforced the reverse. The phone's immunity is occlusion, not design — the sheet happens to cover the button — which is precisely the accidental platform difference decision D5 exists to prevent being reported as deliberate.

Fix. startEdit() now raises the existing pop-up instead of building a rival editor; _fwRaise() is the code popOutNote() already ran, extracted so the two routes cannot drift. saveArt() carries the rule as defence in depth: if any route ever leaves ST.editing true while a window owns the note, it flushes the owner, so navigating away still saves what is on screen.

Open product decision — §7, Decision A.

Finding 2 — HIGH — The published site and public repo carried private data

Reproduction: grep the committed index.html, and repro/export-residue.mjs for the mechanism that produced it.

What was in the shipped file (13,805 bytes of serialised browser debris, at the end of <body>):

  • four Google sign-in <iframe>s pointing at aaas-notebook.firebaseapp.com, each carrying the Firebase API key in its query string — real elements that a visitor's browser would load;
  • a serialised #tab-picker holding four real note titles, four real note IDs and two real folder names (deliberately not reproduced here);
  • the owner's real notebook ID, baked into the Cloud Sync dialog as an input value — dead markup, since openSyncModal() overwrites that node, but readable by anyone who viewed source;
  • #nti-picker, #jrn-picker, a fully-populated #eb-pop toolbar, and a browser extension's <section id="id-recall-widget-root"> with a 5 KB inline style.

How it got there. index.html is, at least in part, a product of the app's own 📦 Save File export, which serialises the live document. A sanitiser (_cleanExportRoot(), v03.80) exists for exactly this and its own comment says the drag ghost must be cleared because "it holds a REAL note title, which leaked private content into Deploy Export files that are meant to be empty shells." It had three gaps:

GapWhy it missed
Sign-in iframesRule 1 removed <script src>, never <iframe src> — though the function's own comment names the sign-in iframe as residue
Extension widgetRule 4 matched [class*="recall-"]; the node had an id and no class
The pickersNothing covered them — they are appended to <body>, and getExportHTML() only clears tree/p2h/p2c/p3h/p3c/ctx/mb

Every allow-list entry named residue someone had already been bitten by. A longer list would have rotted the same way.

Before: all 8 residue kinds survived both exports, including the Deploy Export the code promises is "an empty shell so that visitors who view the page source see no private data". After: 0 of 8 survive; a note's own YouTube embed still does.

Fix. Ask the general question instead of listing ids: _snapshotShell() records document.body's children once at DOMContentLoaded, before the app builds any chrome of its own, and the export drops every body child that was not there. It names nothing, so it covers the pickers, float windows, the sign-in iframe, an extension's widget and whatever is added next — the new app-check invents a popover the app has never heard of and requires it gone. A second rule drops cross-origin iframes wherever they sit, while note embeds inside .embed-wrap are kept. The already- committed residue was deleted from index.html in the same change.

Not fixed, and it cannot be by a commit — see §8. The API key, the notebook ID and the note titles remain in git history.

Finding 2b — HIGH — The same private data is still live in the sealed legacy build, and I may not touch it

This is the half of Finding 2 that is NOT fixed, and it needs your decision.

legacy/v03.99/index.html is a frozen build — a complete sealed copy of the app as it was on 2 September 2026, served publicly at https://siyagah.github.io/legacy/v03.99/. It carries exactly the same residue that was just removed from the live app:

In legacy/v03.99/index.htmlCount

So the leak is not closed by this session's fix — it is closed in the live app and still open one directory away, at a public URL.

Why it was not fixed here. Two of the project's own rules collide:

  • I6 — *"legacy/** is sealed. No feature, no fix, no refactor, no version bump, ever." legacy/README.md is emphatic: "If a bug exists in v03.99/, that bug is part of the record and stays."* ship-check.mjs enforces it by comparing the folder byte-for-byte against origin/main.
  • The privacy problem, which says this file should not be publicly served as it is.

I6 is an explicit, written rule and this is a real privacy exposure; resolving that collision is a product decision, not a judgement I should make quietly on the owner's behalf. Nothing in legacy/ was changed.

The options, for the owner (§8, item 4):

  1. Leave it. Lowest effort, keeps I6 perfectly intact. The exposure continues, and its seriousness depends almost entirely on the Firestore rules question below.
  2. Strip only the residue from the frozen build, leaving its application code untouched, and record the exception in legacy/README.md and CLAUDE.md. This treats "remove leaked private data" as categorically different from "fix a bug", which is arguably the honest reading of a rule written to preserve behaviour.
  3. Unpublish the frozen build — keep it in the repository but stop serving it, or remove it from the public site entirely.

My recommendation, stated as a recommendation and not acted on: option 2. I6 exists so that a version of the app can never be lost to a later change and so there is always a working fallback — deleting a stray sign-in iframe and a picker full of note titles takes nothing away from either purpose, while leaving a real note title on a public URL serves neither.

Finding 3 — HIGH — "Import from JSON backup" destroyed the notebook silently

Invariant broken: I1 again.

Before — the entire function body that mattered:

if(d.folders&&d.articles){ DB=d; persist(); render(); toast('Data imported ✓'); }

A visible button (⬆ Import data from JSON backup) → a file picker → the whole notebook replaced, with no count, no confirmation, no merge option and no way back — and persist() propagates the replacement to every other device.

The standard was already set five thousand lines away: importBackup() counts what is in the file, offers merge-or-replace, and confirms twice before replacing.

Fix. importJSON() now validates the file's shape, shows what the file holds against what the notebook holds now, says plainly that this replaces rather than merges and that it syncs, and writes a complete 📦 Save File recovery copy before touching anything — the app's own recovery mechanism (I4), needing no new storage and no new screen. If that copy cannot be written it says so and asks again.

Open product decision — §7, Decision B.

Finding 4 — MEDIUM — Accessibility beyond colour is essentially unaddressed

Not fixed — out of scope for this session, and a genuine piece of work.

MeasureCount in the whole app

Colour contrast is excellently handled — five rounds of measured WCAG work, swept across five presets and custom colours. But most controls are <div>/<button> with a glyph and a title, driven by click handlers. Practical consequences: much of the app is not reachable by keyboard; a screen reader would announce many controls as unlabelled; menus and dialogs do not trap or restore focus; title is not an accessible name in every context.

Severity judged MEDIUM, not HIGH, on the app's own terms: this is a single-user personal notebook whose one user is not currently reported as needing assistive technology. It would become HIGH the moment that changes, or if the app is ever shared. See §7, Proposal 3.

Finding 5 — MEDIUM — No continuous integration

The project has a real 283-check harness and nothing runs it automatically. There is no GitHub Actions workflow. A merge to main is a deploy, and the only thing standing between a regression and the live site is a developer remembering to run two commands. See §7, Proposal 1.

Finding 6 — LOW / INFORMATIONAL — Firestore may be in test mode

The Cloud Sync setup dialog tells the owner, in step 3: "Build → Firestore Database → Create in test mode". Test mode rules allow anyone to read and write the database. Combined with a public API key and project ID (both of which are meant to be public), the only thing protecting the notebook is the rules.

⬜ Not tested — no access to the owner's Firebase project. This is an owner action, §8, and it is the most important one on the list.

How to trust this document

Three claims in early drafts of this audit were wrong and were caught by measuring rather than reasoning. They are recorded because they say something about how the rest should be read:

  1. "saveArt() is missing the dataset.aid guard that _flushEd() has." It is missing it — but the guard would not have fired. #ed carries the correct note id; it is merely empty. A fix based on this reading would have passed review and left the defect in.
  2. "Navigating away wipes any popped-out note." It does not. The order matters: press ✏ Edit after typing and the note is fine.
  3. "A note does not survive a reload." A test artefact — insertAtCaret() replaces the selection, so the test had erased its own marker text, exactly as tools/README.md warns.

Every finding in this document is backed by a runnable script in audit/repro/ or a check in tools/app-check.mjs. No test is reported as passing here without evidence, and everything that could not be tested is marked ⬜ with the reason.
